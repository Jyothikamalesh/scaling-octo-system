Read this first
Passing 125/125 does not mean the solution handles every scenario. When I tried 27 harder scenarios once, 10 failed: 5 were genuine limitations of the system (section 7). And the verifier has a measured weak spot: a random wrong 1-decimal number passes 33% of the time in a dense payload (section 4). A comprehensive test set is valuable precisely because it reports these, not because it passes.

1The mental model

There are really two different questions, and they need two different kinds of test.

Question A: does the system behave?Given a user request, does the agent pick the right tools, refuse when it should, recover from errors, remember the conversation, and give grounded answers? This is a behaviour question. It needs the real model and real tools, so it is run end to end, a few times, and judged by rules. → the 25 live cases.
Question B: does the detector work?The verifier is a classifier: it looks at a reply and the tool outputs and says “hallucinated” or “fine”. How often is it right, and on which kinds of error? This is a measurement question. It needs many labelled examples, not a model in the loop. → the detection benchmark (precision, recall, F1).
Question C: would the tests notice if it broke?A test set that cannot fail is worthless. So the system is deliberately broken in four ways and the same cases are run again to see which ones fail. → section 8.

Why the live evals score the final reply
The verifier can rewrite a reply before the user sees it, so a passing case means either “the model was right” or “the verifier fixed it”. The runner counts how often the verifier stepped in (5 of 170 turns in the latest run, all in long_session_recall) so a rewrite cannot hide behind a pass.

  • Strong where a claim is attached to a record. A value on the right scene, a weather cell on the right day, scene ids, dates, superlatives and tool citations are caught every time (lowest 95% bound 72%).

Sweeping random wrong values: 75 of 230 (33%) of wrong 1-decimal values pass against a 10-day weather payload (about 40 numbers), but only 51 of 5000 (1%) of 2-decimal values against a 6-scene payload. That is why wrong_average_off_data, predicted “detect”, measured 80%: 15.9 passes because the data holds 15.8 and 16.0. The one prediction that failed was the most informative result.

What each result means

  • M1 weak prompt: the refusal and hallucination cases are blind to the prompt. With every rule deleted, forecast_horizon, insufficient_info_no_place, fabricated_scene_id, no_memory_override_elevation, false_premise_cloud_cover and prompt_injection_user all still passed. They test the model's own good behaviour, not whether the prompt's rules are doing the work. The cases that did fail (imagery_basic, terramind_embed_compare: citations; out_of_scope_general) are the ones that depend on the prompt.
  • M2 verifier off: only 1 of 2 predicted cases. long_session_recall fails (the 31-row table is mis-transcribed); weather_table_ten_days does not (10 rows come out right). So the live evals can only see the verifier working on a failure the model happens to make; the detection benchmark (section 4) is what measures it directly.
  • M3 tool errors swallowed: not detected at all, which exposed a weak assertion. The bad-date case passed even when the model was told “OK” instead of the error, because its regex was satisfied by the model's own knowledge that 30 February does not exist. I added reply_all: ['out of range'] (the tool's own error text must reach the user). Re-run: the broken system now fails that case, and the real system still passes it 5 of 5. terramind_unknown_embedding_id still passes the broken system because the model says the ids do not exist anyway.
  • M4 context amnesia: caught, but the break was too blunt. All three predicted multi-turn cases failed, but so did 14 single-turn cases, because trimming to 700 tokens also drops the current turn. It shows the cases fail when context is destroyed, not that the context cases are specifically sensitive. A cleaner break (drop earlier turns only) would test that.
A mistake worth remembering
My first broken-system runs all “failed” with 0 turns: I had exported the API key with its quotes and every request got a 401. A set of 100 failures looked like perfect sensitivity. I caught it by reading the error, deleted the invalid result files, and re-ran. Always read the failure before believing a test result, including a good one.

9Where a labelled true/false dataset is the better tool

A live case checks a behaviour once. A labelled dataset measures a detector many times. Prefer a dataset when the question is “how often is this right”, the inputs can be made without a model in the loop, and one example means nothing without its near neighbours.

10How EVE itself handles it

From the eve-esa repositories (their READMEs and files as read on 2026-10-04; a reading of the structure, not a code audit).

At run time

The backend has hallucination_detector.py: an LLM judge given the question, the answer, the retrieved documents and the conversation. It returns a binary label (0 factual, 1 hallucination) and a reason. A hallucination label triggers a query rewrite and a new answer.

Keeping the judge fair

A test (test_hallucination_history_prefix.py) makes the detector see the same history prefix the agent saw, and not the answer being judged, so it does not flag an answer just for missing context.

Human signal

Users can give thumbs and hallucination votes on answers; these are sent as scores to Langfuse (langfuse_scores.py).

Offline evaluation

evalkit scores models on labelled datasets: hallucination detection (dataset eve-esa/hallucination, letter answer A/B, accuracy, precision, recall, F1) and refusal (dataset eve-esa/refusal, LLM-as-judge on declining when the documents are insufficient), plus MCQA and open-ended tasks.

  • Give the judge the same context the agent had (their history-prefix test is the model to copy).
  • Collect user votes as a free source of real labelled errors for the dataset in section 9.
  • Use the same metrics (precision, recall, F1): done in section 4, on a different object (an agent's reply against its own tool results, not a statement against a document).

What I would do next, in order

  1. Build the derived-values and technical-identifier datasets (a measured failure on each).
  2. Relabel real stored replies by hand to get an independent set and a real recall figure.
  3. Replace the blunt context break with “drop earlier turns only”, and make the refusal cases fail when the prompt's rules are removed (a stronger assertion or an adversarial phrasing).
  4. Surface ambiguity and the missing clock in the product: both are genuine limitations a user would hit.
  5. Add an LLM judge for qualitative claims, calibrated on the labelled set.

Six things to say about the evals

  • “There are three layers: live cases for behaviour, a benchmark that scores the verifier as a classifier, and offline tests for mechanisms.”
  • “I measure the verifier with precision, recall and F1 per error type, on data it was not built on, with predictions written first.”
  • “It is strong on attribution, ids, dates, superlatives and citations, and weak on plain numbers in dense payloads: a random wrong 1-decimal number passes about a third of the time.”
  • “I broke the system four ways to check the evals notice; that found a weak assertion and showed the refusal cases do not test the prompt.”
  • “The live cases pass; harder scenarios fail in ways I can name: ambiguity, no clock, blank input, derived values.”
  • “EVE judges with an LLM over retrieved text; mine checks against tool outputs with rules. A labelled dataset is how I would calibrate either.”
